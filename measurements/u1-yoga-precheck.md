## 0. 一句话结论

**Go（带两个 CI 阻塞项）**。Yoga 在**所有本机可测的目标上都通过**：

| 前置（主文档 §7） | 本机实测结果 | 判定 |
|---|---|---|
| 静态库增量可接受 | 最优配置下**链接后增量 ≈ 92 KiB（native，94,208 B）/ ≈ 120 KiB（wasm，123,180 B）** | ✅ 通过（阈值见 §5） |
| wasm 目标可编 | emscripten（`--package web` 后端）**零错误编过并链接**；严格 `--target=wasm32-wasip1` 已装 `build-tools/wasi/` 后**本机实测：编+链+运行全通过**（详见 §5.2 / `u1-wasip1-report.md`） | ✅ 通过（本机已测） |
| 与现有裁剪旗标相容 | COFF `-ffunction-sections -fdata-sections` + `/OPT:REF` **实测能剪**未引用 Yoga 函数 | ✅ 通过；macOS `-Wl,-dead_strip` **本机不可测，待 CI** |

**主文档 §7/§8 被修正的假设**（详见 §7）：

1. **体积风险被高估**：§8 把「Yoga 进二进制」列为第一条风险，实测 Yoga 完整布局引擎只占 **≈ 92 KiB**（native，94,208 B）/ **≈ 120 KiB**（wasm，123,180 B），相对本项目 GUI 构建的 MB 量级（`rust-text-backend.md`：画字 6.05 MB）是**零头**。
2. **不存在「需要 CMake 生成配置头」这一步**：`Yoga.h` / `YGConfig.h` 等都是**静态源码头**，`CMakeLists` 只生成一个与头文件无关的 `yogaConfig.cmake`（`find_package` 用）。**19 个 `.cpp` 用 `clang++ -I <repo>` 直接编即可**。
3. **新发现（主文档 §7/§8 未提）**：Yoga 的 `YG_EXPORT` 在 `__EMSCRIPTEN__` 下带 `__attribute__((used))`，**会让 `--package web` 路径把整套 C API 强导出/强保留**，削弱 wasm 侧的 DCE（native/macOS 无此属性）。web 路径的增量由此比 native 大。
4. **新发现**：`-DYG_NDEBUG` 在当前 Yoga 源码里**零引用**，是**空开关**；只有 `-DNDEBUG`（经 `<cassert>`）真正关断言，省 ≈ 27 KB。

### 2.2 **是否需要 CMake 生成配置头？——不需要**

```bash
$ find . -name '*.in' -not -path './.git/*'
./cmake/yoga-config.cmake.in          # 只生成 yogaConfig.cmake（find_package 用）
$ grep -n "configure_file" cmake/*.cmake yoga/YGMacros.h
（无输出 —— 没有任何 configure_file 生成头文件）
$ grep -rn "Version.h\|YGVERSION" yoga/*.h cmake/*.cmake.in
（无输出 —— 库本身不带版本头）
```

- **入口头/ C API 头**：`#include <yoga/Yoga.h>`（伞头）即可；公开 C API 全在 `yoga/YG*.h`。
- `yoga/YGEnums.h` 顶部标 `@generated by enums.py`，但该文件**已 checked-in**，构建**不需要**再跑 `enums.py`。
- `YG_EXPORT` 在 `YGMacros.h` 里**按平台就地 `#define`**（非生成）。**结论：接 Yoga 不需要 CMake，也不需要任何生成步骤**——把 19 个 `.cpp` + `-I <repo根>` 交给 clang++/em++ 即可。

### 2.3 静态库构建（Windows x86_64-msvc 基数）

```bash
# build-yoga.sh <name> <flags...>   —— 逐 TU 编译 + llvm-ar rcs
$ bash build-yoga.sh o2-fs -O2 -DNDEBUG -DYG_NDEBUG -ffunction-sections -fdata-sections
config=o2-fs
objects=19
obj_total_bytes=458226
a_bytes=509762
```

单条命令形状（19 个 `.cpp` 各一次，再归档）：

```bash
clang++ -std=c++20 -O2 -DNDEBUG -DYG_NDEBUG -ffunction-sections -fdata-sections \
        -I <yoga-src> -c yoga/<f>.cpp -o <f>.o
"/c/Program Files/LLVM/bin/llvm-ar.exe" rcs libyoga.a <所有 .o>
```

> 与 Yoga 自己的 CMake Release 口径一致（`cmake/project-defaults.cmake` 就是
> `-O2 -ffunction-sections -fdata-sections` + `-Wl,--gc-sections` / AppleClang `-Wl,-dead_strip`），
> 所以「手编」与「CMake 编」产出等价，只是省掉 CMake 这一层。

### 2.4 C++ 依赖是否引入 libstdc++/libc++ 运行时开销？——量了，极小

本机是 MSVC ABI，**没有 `-lstdc++` 这个名字**；等价实验是「C 驱动 vs C++ 驱动」：

```bash
$ clang   -O2 tmp/c_floor.c -o build/c_floor.exe;      # C 驱动
$ clang++ -O2 tmp/c_floor.c -o build/c_floor_cpp.exe;  # C++ 驱动（同一份 printf 程序）
c_floor(printf)                  120832 B
c_floor_cpp                      120832 B        ← 完全相同
```

- **一个不碰 C++ 库的程序，用 C++ 驱动编，增量 = 0 B**（静态 CRT 已在两者中）。
- Yoga 实际从 MSVC 静态 C++ 运行时（`libcpmt`）拉进来的**只有 2 个成员**（链接器 `/MAP:` 证据）：

```
libcpmt:vector_algorithms.obj     # std::find 的向量化实现（__std_find_trivial_8 等）
libcpmt:xthrow.obj                # std::bad_alloc/bad_function_call/logic_error/length_error/out_of_range
```

（`xthrow` 出现是因为 Yoga 用了 `std::vector`/`std::function`/`std::unique_ptr`，MSVC STL 的
`_Xlength_error` 等即便 `-fno-exceptions` 也仍引用；`-D_HAS_EXCEPTIONS=0` 实测**反而略大**
215552 vs 215040，故不采用。）
- **对真实目标（macOS）的推断（未测，待 CI）**：libc++ / libc++abi 是系统自带 dylib，
  正常不静态链入；且 Yoga 在非 MSVC、非 emscripten 平台的 `YG_EXPORT` 只是 `visibility("default")`。
  预期运行时开销 ≈ 0，但**本机不可测**。

**小结 M1**：Yoga 是「19 个 `.cpp`、无 CMake 生成步骤、C++ 依赖只碰 2 个运行时成员」的可直接编译库。

## 3. M2 — 体积矩阵

### 3.1 归档 / 对象（native，19 个 `.cpp`）

| config | opt | 附加旗标 | `.o` 总和 (B) | `libyoga.a` (B) |
|---|---|---|---|---|
| `o2-nofs` | `-O2` | （无 fs） | 409,551 | 461,086 |
| `o2-fs` | `-O2` | `-ffunction-sections -fdata-sections` | 458,226 | 509,762 |
| `os-fs` | `-Os` | fs | 444,964 | 511,876 |
| `oz-fs` | `-Oz` | fs | 562,303 | 667,802 |
| `o2-fs-noexc` | `-O2` | fs + `-fno-exceptions` | 367,224 | 415,064 |
| **`oz-fs-noexc`** | `-Oz` | fs + `-fno-exceptions` | **499,063** | **603,596** |
| `oz-fs-noexc-assert` | `-Oz` | fs + noexc，**断言开**（无 NDEBUG） | 508,976 | 615,860 |

> **反直觉但实测**：`-Oz` 的 `.o`/`.a` **比 `-O2` 大**（`-Oz` 抑制内联 → 函数更多更肥 + 每函数分节对齐），
> 但**链接后反而最小**（见 §3.2）。这正说明**要拿最终可执行体积做判据，不能拿 `.a` 体积**。

### 3.2 最终可执行增量（关键指标）

做法：同一份最小 C 程序 `tmp/yoga_min.c`（建 3 个节点、设 flexDirection/size/flexGrow、算一次布局、
读回宽度）；地板 = 同用 printf 的空程序。**地板 120,832 B**。

```bash
# 地板
$ clang   -O2 tmp/c_floor.c -o build/c_floor.exe        # 120832 B
$ clang++ -O2 tmp/c_floor.c -o build/c_floor_cpp.exe    # 120832 B
# 链接（clang++ 自动带 C++ 运行时；/OPT:REF /OPT:ICF = COFF 的 gc-sections / ICF）
$ clang++ -O2 tmp/yoga_min.c -I yoga-src build/<cfg>/libyoga.a -Wl,/OPT:REF -Wl,/OPT:ICF -o out.exe
```

| 配置 | `yoga_min.exe` (B) | **增量 (B)** |
|---|---|---|
| `o2-nofs` | 297,984 | 177,152 |
| `o2-fs` | 263,168 | 142,336 |
| `o2-fs-nogc`（不加 /OPT:REF） | 263,168 | 142,336（**与 gc 逐字节相同**，见 §4.1） |
| `os-fs` | 227,328 | 106,496 |
| `oz-fs`（异常开） | 224,768 | 103,936 |
| `o2-fs-noexc` | 247,808 | 126,976 |
| **`oz-fs-noexc`（最优）** | **215,040** | **94,208** |
| `oz-fs-noexc` + 项目旗标 `-fms-runtime-lib=static` | 214,528 | **93,696** |
| `oz-fs-noexc-assert`（断言开） | 242,176 | 121,344 |

**结论**：
- **最优 native 增量 ≈ 92.0 KiB（94,208 B）**（`-Oz -DNDEBUG -DYG_NDEBUG -ffunction-sections -fdata-sections -fno-exceptions` + `/OPT:REF`）；换项目旗标 `-fms-runtime-lib=static` 为 **91.5 KiB（93,696 B）**。
- `-DNDEBUG`（断言关）值 **≈ 26.5 KiB**（121,344 → 94,208）。
- `-fno-exceptions` 值 **≈ 9.5–15 KiB**（`-Oz` 档 9,728 B；`-O2` 档 15,360 B）。
- `-ffunction-sections -fdata-sections` 值 **≈ 34 KiB**（`-O2`：177,152 → 142,336；它同时是 DCE 的前提）。
- **`-DYG_NDEBUG` 是空开关**：`grep -rn YG_NDEBUG yoga-src/yoga/` **零命中**。

## 4. M3 — 死代码消除（DCE）相容性

### 4.1 本机（COFF / `lld-link`）：对应旗标是 `/OPT:REF`

```bash
$ clang++ -O2 tmp/yoga_min.c -I yoga-src build/o2-fs/libyoga.a -Wl,--gc-sections -o yoga_gc.exe
lld-link: warning: ignoring unknown argument '--gc-sections'      # ← --gc-sections 被忽略！
```

- **GNU 拼写 `-Wl,--gc-sections` 在 `lld-link` 上被静默忽略**；COFF 的等价物是 **`/OPT:REF`**（丢无引用函数/数据）+ **`/OPT:ICF`**（折叠相同 COMDAT）。
- **实测 `/OPT:REF` 在 `lld-link` 上默认就开**：加不加 `/OPT:REF`，产物**逐字节相同**（`cmp` 通过）。
  真正起作用的是**编译期**的 `-ffunction-sections -fdata-sections`（把函数变成可独立丢弃的 COMDAT）——与 `build.ts` 里「ELF/COFF 的 `--gc-sections` 需编译期分节」的注释一致。
- **实测剪枝生效**（同一最优配置 `oz-fs-noexc`）：

| 程序 | 引用的 API | `exe` (B) | 增量 (B) |
|---|---|---|---|
| `yoga_one` | 仅 `YGNodeNew/Free`、`YGConfigNew/Free` | 164,864 | 44,032 |
| `yoga_min` | + `CalculateLayout` + 少量 setter | 215,040 | 94,208 |
| `yoga_many` | + 约 20 个 setter/gap/wrap/percent | 217,600 | 96,768 |

`yoga_one` 的链接器 `/MAP:` 里**根本没有** `yoga_algorithm_CalculateLayout.cpp.o`（只有
`Config/Log/event/Node/YGConfig/YGNode/PixelGrid/AssertFatal`），证明**布局核心被整块剪掉**。

**关于「是否随引用量线性增长」——不是线性**：增量由**布局核心**支配（`one → min` 跳 **+50 KB**），
之后再加约 20 个 setter 只多 **+2.5 KB**。原因是链接以**归档成员（TU）**为粒度拉取：
`YGNode.cpp.o` 一旦被引用，其内的 `CalculateLayout` 就整块进来；而未触碰的 TU
（`YGNodeStyle.cpp.o` 等）整个不拉。所以「只做基础布局、不碰 grid/baseline/wrap」的小程序，
**不会**为那一大票 setter 付钱。

### 4.2 macOS `-Wl,-dead_strip`（主文档 §7 明确点名的口径）——**本机不可测，待 CI 验**

- 本机无 macOS、无 ld64，**无法实测 `-Wl,-dead_strip`**。
- 静态证据（可复核）：在 Apple 平台，Yoga 的 `YG_EXPORT` 是 `__attribute__((visibility("default")))`
  （`YGMacros.h`），**不带 `used`**；`visibility("default")` 不阻止 `ld64 -dead_strip` 丢无引用块，
  且 Yoga 自带的 CMake Release 就是 `-Wl,-dead_strip`（`cmake/project-defaults.cmake`），说明
  「`-dead_strip` + Yoga」是其**官方支持组合**。
- **判定：待 CI（arm64 macOS）复跑**：`clang -O2 -ffunction-sections -fdata-sections … -Wl,-dead_strip` 下
  「`yoga_one` 明显小于 `yoga_min`」应成立。

## 5. M4 — wasm 可编性

### 5.1 emscripten（`--package web` 路径）：**零错误编过**

```bash
$ for f in $(find yoga-src/yoga -name '*.cpp'); do \
    em++ -std=c++20 -O2 -DNDEBUG -DYG_NDEBUG -ffunction-sections -fdata-sections -I yoga-src -c $f -o …; done
compiled 19 files / 19 .o   （wasm-matrix.log 里 "error" 命中 0 次）
$ emar rcs build/wasm-obj/libyoga.a build/wasm-obj/*.o
$ em++ -O2 -sSTANDALONE_WASM -I yoga-src tmp/yoga_min.c build/wasm-obj/libyoga.a -o build/wasm_yoga_min.wasm
$ ls -la build/wasm_yoga_min.wasm   → 125252 B
$ em++ -O2 -I yoga-src tmp/yoga_min.c build/wasm-obj/libyoga.a -o build/yoga_web.js  → 125404 B wasm + 50149 B js
```

- **19/19 编过，0 error**（只有 143 条 `used attribute ignored on a non-definition declaration` 的**警告**，来自 `YG_EXPORT` 的 `used` 落在头文件声明上，无害）。
- **能跑吗？——本机不能**：`which wasmtime wasmer wasm3` **全部缺失**，故只报「可编可链」，**未运行**。
- **WASI 形状验证**：`-sSTANDALONE_WASM` 产物只 import **`wasi_snapshot_preview1`**（`fd_write`/`proc_exit`，
  加 Yoga 后多出 `fd_close`/`fd_seek`），与项目 `--target wasm` 的 WASI 模块**同 ABI 形状**：

```
build/wasm_floor.wasm (2072 B):    wasi_snapshot_preview1: 2 imports
build/wasm_yoga_min.wasm (125252 B): wasi_snapshot_preview1: 4 imports (fd_close, fd_seek, fd_write, proc_exit)
```

- **与 emscripten `--package web` 共存**：直接用 em++ 默认（JS glue）把「C 程序 + `libyoga.a`」链成
  `.js + .wasm` 成功（`yoga_web.js` 50 KB / `yoga_web.wasm` 125 KB）——即接缝库可作为 `objects`/`sources`
  交给 emcc，与生成的 `.c`（C）和语法胶水（`-std=c++17`）**并存无冲突**。

### 5.2 严格 `--target=wasm32-wasip1`（项目 `--target wasm` 的真实形状）：**本机已测**（能力通过；预算见 [`u1-wasip1-report.md`](./u1-wasip1-report.md)）

> **历史陈述（保留）**：本节最初记为「**本机不可测**」——当时本机没有 WASI sysroot，
> 下面这段报错是当时的真实记录。后来在 `build-tools/wasi/` 装好 wasi-sdk 34 sysroot + wasm
> builtins 后已可本机实测，结论见 `u1-wasip1-report.md`。

```bash
# 当时的真实报错（修复前；现已有 build-tools/wasi/ 的 --sysroot/-resource-dir）
$ clang --target=wasm32-wasip1 w.c -o w.wasm
wasm-ld: error: cannot open crt1.o: no such file or directory
wasm-ld: error: unable to find library -lc
wasm-ld: error: cannot open C:\Program Files\LLVM\lib\clang\23\lib\wasm32-unknown-wasip1\libclang_rt.builtins.a: no such file or directory
clang: error: linking with exit code 1
$ echo $WASI_SDK_HOME
<unset>
```

- **当时根因 = 环境缺 WASI SDK / wasi-libc sysroot**（`build.ts:1110/1406/1432` 要求 `WASI_SDK_HOME` 提供
  `wasm32-wasip1` 的 `crt1.o` + `libc` + `libsetjmp.a`）。**这与 Yoga 无关**——同一个桩 C 程序也编不过。
- **现在（已修复）**：`build-tools/wasi/{wasi-sysroot-34.0,resource-dir}` 就绪后，`clang --target=wasm32-wasip1`
  编 + 链 Yoga **成功**，30 个 seam 函数 + 17 项验收测**实跑通过**（`17 checks, 0 failures`）。
- **判定：本机已测——能力✅；预算✅**（`yoga_min` 剥离后 116.1 KiB / 增量 110.8 KiB、`seam_test` 136.7 KiB /
  增量 131.5 KiB，均 ≤ 192 KiB；`-Oz -flto` 下 `yoga_min` 81.5 KiB / `seam_test` 90.0 KiB，增量 76.3/84.8 KiB）。原本「≤192 KiB 不达标（343.6 KiB）」是**旧的裸链接口径**（未带项目默认
  的 `-Wl,--strip-debug`，把 wasi-sdk 预编译 libc 自带的 ~205 KiB DWARF 也算进去了）。
  **完整数据、归因拆解、缓解矩阵与复现步骤见 `u1-wasip1-report.md`。**

### 5.3 新发现：`used` 属性削弱 `--package web` 侧的 DCE

```c
// tmp/vis2.c：两个 default-visibility 函数，一个带 used，一个不带；main 不调用二者
__attribute__((visibility("default"), used)) int vis_used(int x){…}
__attribute__((visibility("default")))        int vis_plain(int x){…}
$ emcc -O2 -sSTANDALONE_WASM build/vis2.a -o build/vis2.wasm
exports: memory, vis_used, _start, …     # ← 只有带 used 的被导出/保留；vis_plain 被丢
```

`yoga/YGMacros.h`：

```c
#if defined(__EMSCRIPTEN__)
#define YG_EXPORT __attribute__((visibility("default"), used))   // ← 带 used！
#elif !defined(_MSC_VER)
#define YG_EXPORT __attribute__((visibility("default")))
#else
#define YG_EXPORT
#endif
```

后果：**在 `--package web`（emcc 定义 `__EMSCRIPTEN__`）路径上，Yoga 公 C API 会被 `used` 强制保留并进入导出表**
（实测 `wasm_yoga_min.wasm` 的导出表里挂满 `YGNodeStyleSet*`），DCE 弱于 native。
`-sEXPORTED_FUNCTIONS` 限流**不能**阻止它（实测把导出限成 `_start` 后产物**反而更大** 136,892 B、YG 符号仍在）。
- 在 macOS（`visibility default`，无 `used`）与 `--target wasm32-wasip1`（clang，无 `__EMSCRIPTEN__`）上**无此问题**。
- **给 U1 的启示**：web 路径要么接受这更大的体积（已计入 §3.3 的 120 KiB / 123,180 B），要么在粘合层编译 Yoga 时**抑制该 `used`**
  （例如给出一个本地 `YG_EXPORT` 覆盖或用 `-fvisibility` 组合）——属 U1 实施细节，本文不展开。

## 6. M5 — 预算结论

### 6.1 预算门槛（含依据）

以 `size-optimization.md` 的现有基线为参系：本项目**对体积极敏感**（画文字构建 19.43 → 6.05 MB 是
专门做过两刀才降下来的）。故设两道门，**结构性 + 数值性**：

| 门 | 内容 | 依据 | 实测 |
|---|---|---|---|
| **A（硬门，必须）** | **不用 `asaot.ui` 的构建，Yoga 增量 = 0 B** | 同 `sqlite`/`skia_text_glue` 的「引用才链」（`index.ts:933` 只在 `usesFlashData` 时 push 源码）；`-O2` 从 `main` 出发可达性剪枝 | ✅ 机制现成；测得未引用时布局核心能整块剪掉（§4.1） |
| **B（数值门，UI 构建）** | Yoga 增量 **native ≤ 128 KiB、wasm ≤ 192 KiB** | UI 构建必然已链渲染器（Skia 画字 6.05 MB 量级），Yoga 占比 < 3%（噪声级）；128/192 KiB 是在实测 92.0/120.3 KiB 上留 ~30–60% 余量 | ✅ **92.0 KiB（94,208 B）/ 120.3 KiB（123,180 B）** |
| **C（能力门）** | 必须能编 wasm | 主文档 §7 前置 | ✅ emscripten ✅；wasip1 **本机已测通过**（§5.2） |
| **D（DCE 门）** | 未引用的 Yoga API 必须能剪 | §8 靠「引用才链」 | ✅ COFF 实测可剪（§4.1）；macOS **待 CI** |

### 6.2 Go / No-Go

**Go（条件）**：三门中 A/B/D 本机实证通过；C 在本机当时只能证到「emscripten 零错误 + WASI 形状」。
**wasip1 现已本机实测通过（见 `u1-wasip1-report.md`），只剩 macOS `-dead_strip` 一项本机不可测**。因此定为**「Go，但剩下的 CI 阻塞预检任一红即回退」**：

1. **CI 阻塞项 ①**：~~`WASI_SDK_HOME` 就绪的 CI 上，`clang --target=wasm32-wasip1` 编 + 链 Yoga 成功，且 wasm 增量 ≤ 192 KiB。~~
   → **本机已测（不再是阻塞项）**：能力**通过**（30 函数 + 17 用例 `17 checks, 0 failures`）；预算**通过**
   （剥离后增量 `yoga_min` 110.8 KiB / `seam_test` 131.5 KiB ≤ 192 KiB）。见 [`u1-wasip1-report.md`](./u1-wasip1-report.md)。
2. **CI 阻塞项 ②**：macOS arm64 上，`-ffunction-sections -fdata-sections` + `-Wl,-dead_strip` 下 `yoga_one < yoga_min`（本机 COFF 实测增量量级：≈ 43 KiB vs ≈ 92 KiB，绝对值因动态 libc 会不同）。
