# 第十八轮：`./build.sh web` —— 同一个 AS3 树，第三个运行时（浏览器）

> 用户要求：给 `ui-demo/air-gallery/build.sh` 加一个「编译到 web」的选项，用法 `./build.sh web`，
> **不得破坏既有的默认（AIR）臂**。
>
> 结论：`./build.sh web` 已可用 —— 它把**同一份** `demo/**` + `kit/` + `seam/` 编成
> **wasm32**（Emscripten），落到一个独立的暂存目录，然后用一个带 `application/wasm` 的
> 本地静态服务器把它打开。默认臂、`aot`、`swf`、`desc`、`clean` 的行为**逐字未变**
> （`desc` 的输出由 `tools/buildsh-gpu.cjs` 继续钉着，本轮的 52 道门里它仍是绿的）。

## 1 为什么值得单开一条臂

一条 AOT 编译器最容易被怀疑的地方，是「它只是碰巧在你那台机器上跑出了一个窗口」。
现在同一棵树有三个运行时：**AIR**（参考，`mxmlc → adl`）、**原生 AOT**（我们的产物）、
**浏览器**（wasm32）。三者跑同一份 AS3 源码、读同一份 `app.xml`。任何「这是 C 本地
语义的巧合」的怀疑，都可以用第三份产物去证伪或证实 —— 而这只需要一条命令。

## 2 它和另外两条臂为什么不能共用一个运行器

窗口是**一个可执行文件**开的，页面不是。所以 `run-gallery.cjs` 的那三件事
（拉起进程 / 等 `gallery.done` / 用 `Stage.render` 出图）在 web 臂上**一件也用不了**：
没有进程、没有完成标记、也没有 `Stage.render`（那是 AOT 专属测试钩子）。
于是新写了 `ui-demo/web-gallery.cjs`：

1. **找 emsdk**（`EMSDK_HOME`/`EMSDK`，否则本工作区的
   `build-tools/skia-src/third_party/externals/emsdk`）。**显式指定而指错 ⇒ 直接报错**，
   不回落到工作区那一份（否则会用一条没人点名过的工具链建出页面，且全程无声）。
2. **暂存 `../air-gallery-web/`**：`app.xml` 与 `as-image.png` 从 `air-gallery/` **逐字节拷**
   （sha256 校验）、外加一个 `.ttf`（wasm 读不到宿主字体，必须随页发）、`demo/**` 交给
   `stage-air.cjs` 灌进 `src/`。
3. **编**：`as-aot --air-app <web>/app.xml --main-class demo.DocsWeb --target wasm --package web
   -o <web>/GalleryApp --as-class-path ../seam --as-class-path ../kit`。
4. **验产物 + 起服务**：`.html/.js/.wasm` 缺一个就非零退出；服务器带正确 MIME
   （`.wasm` 必须是 `application/wasm`，否则浏览器拒绝实例化）。

入口类是**第三个** `DocsWeb`，不是复用 `DocsAir`；原因不是洁癖：`DocsAir` 建了
`UncaughtErrorEvent`（本编译器未实现），**wasm 编不过**；`DocsMain` 又要 `Stage.render`
钩子。三个臂三个入口，各自只写自己那十行。

## 3 撞上的底层缺口：**G27**（windows 上 spawn 不了 `emcc`）

`as-aot --package web` 是直接 `spawnSync(<EMSDK_HOME>/upstream/emscripten/emcc, …)`，
**不经 shell**，环境里只塞一个 PATH（而且是用 `:` 拼的 POSIX 形态）。在 emsdk 里那个
`emcc` 是 `#!/bin/sh` 脚本，Windows 上：

```
spawnSync(<emsdk>/…/emcc,      ['--version'])  ->  error.code === 'ENOENT'
spawnSync(<emsdk>/…/emcc.bat,  ['--version'])  ->  error.code === 'EINVAL'   (Node 不肯裸跑 .bat)
cmd /c <emsdk>\…\emcc.bat --version            ->  emcc 3.1.44                (能跑)
```

而编译器报的是 `emcc not found: …` —— **文件明明在那儿**，文案把人往错方向带。

**绕行（本工作区不碰 `as3compiler/`）**：`tools/emcc-launcher.c` —— 一个 4.5 KB 的手写 C
程序，`clang -O2` 编成 `emcc.exe`，读同目录 4 行配置（`EM_CONFIG` / `EMSDK_PYTHON` /
`emcc.bat` 路径 / Windows 形状的 PATH），恢复环境后用 `cmd /c` 把 argv 原样转给 `emcc.bat`。
`web-gallery.cjs` 把它编到 `.scratch/emcc-shim/upstream/emscripten/emcc.exe`，再把
`EMSDK_HOME` 指到那个 shim 根 —— **编译器看到的路径与它在 POSIX 上看到的完全同构**。
G27 修好那天，shim 与 `emcc-launcher.c` 可以整体删除（登记见 `compiler-gaps.md` G27）。

## 3b 收口：G27 修好之后，绕行整体删除（第二十轮，同日）

as-aot **v0.4.240**（阶段二百七十六）把 G27 修在编译器里：`emccPath()` 在 win32 选
`emcc.bat` 并走 `cmd /d /s /c`、`PATH` 用 `path.delimiter`、子进程环境继承宿主、诊断区分
「不在」与「在但起不来」。于是本工作区上表那套绕行**只剩成本**，逐处撤除：

| 当时的妥协 | 现在 |
|---|---|
| `tools/emcc-launcher.c`、`shimHomeForWindows()`、`.scratch/emcc-shim/` | **删**；`EMSDK_HOME` 重新就是真 SDK |
| `--check` 自己 spawn `emcc`（还故意用 `:` 拼 PATH 复刻坏环境） | 问编译器：`as-aot doctor --json --target wasm --package web`，报告它**实际会启动的程序** |
| `findEmsdk()` 接受 `emcc` 或 `emcc.bat` | 按平台只认一个，与 `emccPath()` 对齐 |
| 门 A1 钉「三连版本号」 | 钉「编译器说 ok **且**那个程序就在 `$EMSDK/upstream/emscripten/` 里」（反 shim）+「存在但退出 1 的 emcc 必须判不可用」 |
| 变异 M3（launcher `return 127`） | 「门不再相信编译器的结论」；新增 M7「又把 SDK 外面的 emcc 报出来」 |

真编译验证（**全程无 shim**）：`./build.sh web --no-serve` ⇒ exit 0，`GalleryApp.html/js/wasm/data`
（wasm 7.02 MB），页面在 Chromium 里真画出 Getting started 页。

## 4 它到底像不像

`./build.sh web --no-serve` 三次都 exit 0，产物 `GalleryApp.{html,js,wasm,data}`（wasm 7.01 MB）。
把页面在 Chromium 里打开并与**原生臂**的 `air-gallery/gallery-page0.png`（同为 1500×1050）逐项对比：

| 量 | 结果 |
|---|---|
| canvas 尺寸 / 页面标题 | **1500×1050（CSS 1000×700）、`asaot.ui - component documentation`，完全一致** |
| 最常见的 8 个颜色 | `#ffffff`/`#f8fafc`/`#0f172a`/`#fbfdff` 四大块**像素数相差 ≤ 0.9%**；`#e8edf5` **18812 = 18812**；`#dce6f0` 8368 vs 8370 |
| 48 点（8×6 网格中心）采样 | **44/48 逐点相同**；不同的 4 点全在**同一行文字**（y=788）上，是字形像素 |
| 全图墨量（非白像素） | web **317,406** vs 原生 **320,942**（−1.1%）；深墨 287,834 vs 290,573（−0.9%） |
| 全图逐像素 | 79,884 px（**5.1%**）差值 >32 —— **全部落在文字墨迹上**；纯色块、边框、块几何 0 差异 |
| 交互 | 在浏览器里点侧栏一项，画面换页（首帧哈希 `1883718146` → 另一帧），与原生臂一致 |

**v0.4.239（Graphics 开抗锯齿）之后重测**（两个臂都重出图）：**46/48 逐点相同**，剩下的两个点
仍在同一列文字上；墨量 −0.85%；最常见的 8 个颜色里 7 个差 ≤0.35%，唯一超过的是按钮蓝
`#2563eb`（−5.1%，它的纯色像素数由标签字形的覆盖率决定 —— 又是字体）。

**文字为什么不能逐像素相同**：页面要**自带字体**（wasm 读不到宿主字体，`font-urls` 决定
随页发哪一份），原生臂用的是**系统字体**。同一段文字、同一套块几何，字形栅格化
（hinting/亚像素）与文本框内基线可以差几个像素 —— 上表「墨量差 1.1%、差值全在文字上、
块几何 0 差异」就是这个结论的证据。**要钉死到逐字节，需要两个臂用同一个字体文件**；
那会把原生臂从「系统字体」这条真实路径上拽下来，本轮不做，在这里写明。

> 参考帧的版本也说清楚：上面用的 `gallery-page0.png` 是 **HEAD 里那一份**。随后跑全量时这道门
> 会用**当时（另一会话正在改）的编译器**重出图中途覆盖它，同一页新旧两份差 **556 个像素**
> （全图 1.5 M，0.03%，最大差 121，全在内容区）—— 与本轮的 79 884 个差值像素（5.1%）相比可忽略，
> 所以上面的结论不受影响。（那批重出的图**没有**提交，见 §8。）

## 5 工具化：一道门 + 6 个变异

全量构建约 3 分钟，不适合每次门都跑；但**「文件在那儿」和「它跑得起来」是两件事**，
而这正是 web 臂最容易假绿的地方。所以 `tools/buildsh-web.cjs`（**26 项，~5 s，不编译**）
驱动 `bash build.sh web --check` —— **同一个决策路径，把构建去掉**：

- 工具链（**第二十轮已改**）：旧版自己 spawn `emcc --version`（那是 G27 时代唯一能观测
  launcher 活着的证据）；现在**问编译器** —— `as-aot doctor` 的 `web.emsdk` 就是构建开跑前
  跑的那个 `webToolchainError()`，并额外要求它报出的程序恰好是
  `$EMSDK/upstream/emscripten/emcc(.bat)`（**中间不许有东西**），再加一条反面用例：一个
  **存在但退出 1** 的 `emcc.bat` 必须被判不可用；
- argv：`--target wasm` / `--package web` / `demo.DocsWeb`（且**不许**是 DocsAir/DocsMain）/
  `--air-app <web>/app.xml` / `-o <web>/GalleryApp` / 两条 `--as-class-path`（seam、kit）/
  **不许**带 `--gpu-backend`。打印的就是构建**会 exec 的那个数组**（一个定义、两个消费者），
  不是手抄的一份描述；
- 描述符即窗口：报出的尺寸必须等于 `air-gallery/app.xml` 的 `<width>×<height>`（**从 app.xml
  读，不写死 1000×700** —— 改窗口尺寸不该弄红这道门），且 `app.xml` 事后逐字节不变；
- 拒绝：`web --gpu gl`（浏览器自己合成）、未知 flag、指错的 `EMSDK_HOME`；
- 暂存目录**必须仍在库外**（`.gitignore` 的 `air-*` 例外会把它的 `app.xml`/`as-image.png`
  重新拉回来 —— 这条是靠 `git check-ignore --no-index` 查的，不是读文件猜的）。

`tools/mutation-buildsh-web.cjs` ⇒ **7/7 CAUGHT**，每次按 sha256 逐字节还原，且在还原后再跑
一次门确认是绿的：

| | 变异 | 门报的错 |
|---|---|---|
| M1 | argv 里去掉 `--package web` | `the build asks for the web package` |
| M2 | 入口类换成 `demo.DocsAir` | `the entry class is demo.DocsWeb` + `not DocsAir/DocsMain` |
| M3 | `--check` 不再相信编译器（任何 status 都算过） | `an emcc that exists but exits nonzero is NOT reported as usable` |
| M4 | `--gpu` 守卫的比较写成 `wbe`（守卫不再触发） | `` `web --gpu gl` is refused with a reason `` |
| M5 | `.gitignore` 删掉暂存目录那条规则 | 三条 `is git-ignored` 全红 |
| M6 | `findEmsdk` 在 `EMSDK_HOME` 指错时静默回落到工作区 SDK | `is an error, not a fallback` |
| M7 | 报告一个 SDK 外面的 emcc（shim 复辟的形状） | `the program it names is the SDK's own …` |

M3 是这道门存在的理由：一个**存在、名字对、大小对**的 `emcc.bat`，只有真的去跑才发现它
不干活（旧 M3 是同一课的 launcher 版：`return 127` 的 4.5 KB 合法 PE，G27 修好后连同 launcher
一起退役）。M5 是**顺序**的教训：`.gitignore` 里 `air-*` 的 `!` 例外写在前面，暂存目录那条
必须写在**后面**才能盖住它们。

## 6 这道门看不见什么

1. **编译本身**。`--check` 不跑编译器：一个编译到一半失败的 web 构建，`--check` 仍是绿的。
   这一半由第 4 节那次人工测量兜着（三份产物、7.01 MB wasm），以及「页面打开后画出了东西」
   这个事实 —— 但它不是自动门。
2. **页面像素**。没有一条门断言「浏览器画出来的图和 `gallery-page0.png` 像」。做这件事需要
   一个能截图的无头浏览器 + 一个容差策略，而容差策略正是第 4 节那个字体问题在拦路
   （先把字体统一，才谈得上逐像素门）。
3. **浏览器兼容性**。只在 Chromium 上开过。Safari/Firefox 的 canvas 2D 与 WebGL 差异
   完全没测。

## 7 复现

```sh
cd asaotui/ui-demo/air-gallery
./build.sh web --check        # ~0.3 s：编译器自报能否起 emcc + argv，不编译
./build.sh web --no-serve     # ~3 min：出 GalleryApp.{html,js,wasm,data}
./build.sh web                # 同上，然后起服务并打开页面
./build.sh web --serve-only   # 不重建，重开已有产物
./build.sh clean              # 连 air-gallery-web/ 一起删

cd asaotui
node tools/buildsh-web.cjs            # 26 checks, 0 failures
node tools/mutation-buildsh-web.cjs   # 7/7 CAUGHT
node tools/gates.cjs                  # 52/52（含上面这道）
```

> **踩过的坑（给下一个人）**：变异机被外层超时杀掉时，`finally` 没机会跑，`build.sh` 会
> **留在变异状态**（本轮实测过一次：`[ "$ARM" = wbe ]` 被留在了树里）。所以变异机最后
> 一定要再跑一遍门（本文件那台会），并且**收尾前先 `git diff` 看一眼**。

## 8 顺带看见的一次假红（不是本轮改动引起的）

本轮全量的**第一次**跑（第 15 道门 `probe redraw`、开跑 3 分 24 秒时）在 `probe redraw` 上红了：

```
PROBE redraw: 14 checks, 1 failures
  FAIL  program verdict: FAIL a paint-only change re-solved layout 1 time(s);
```

那一刻机器上还挂着一个 Chromium 页面（正在按帧重绘 wasm canvas）、一个静态服务器和两个
轮询进程。随后做过的检查：**单独跑 3 次全绿**；**6 份并发副本全绿**；**12 份并发副本 +
8 个满载 CPU 的自旋进程全绿**；把负载清掉后**再跑一次全量 52/52 全绿**
（`reviews/gates-all-31.txt`）。所以**没能复现**。

它能产生假红的机制是清楚的，写在这里给下一个人：`UiApp` 每帧除了等 `Event.RESIZE`，还
**额外比一次 `stage.stageWidth/stageHeight`**（`kit/asaot/ui/UiApp.as:368`），窗口真实尺寸
晚到就会补发一次 `invalidate(Dirty.STRUCTURE)` ⇒ **正好 1 次** `layoutSolves`。而探针在
`t=900 ms` 抓基线、`t=1400 ms` 收尾，所以「尺寸恰好在 900–1400 ms 之间到达」就会让 (2) 号
断言（paint-only 不许解算）变红 —— 那不是库的缺陷，是探针把「窗口尺寸变更」也算进了被测
对象。**没有去改这个探针**：改一个复现不了的夹具比留着这条记录更糟；真再见到它，先量
`stageWidth` 与 `_solvedW` 的时序，而不是去读 paint 路径。

**这次全量还顺手重出了 `gallery-page*.png` 与 `g19` 的对照文本**（每道门都会覆盖自己的证据）——那批图
是用**另一会话正在改的编译器**画的，不属于本轮，已 `git checkout --` 退回 HEAD；提交里只留本轮
自己的改动（外加 `probes/g11-nondeterminism/run-2026-10-25.txt` 追加的那一次确定性测量，它正是
「在哪个树状态下测的」的记录）。
