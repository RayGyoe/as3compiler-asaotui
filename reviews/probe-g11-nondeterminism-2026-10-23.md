# G11 结案：不是「生成器不确定」，是**在另一个进程正改写的编译器树上测量**

- 日期：2026-10-23
- 结论：`compiler-gaps.md` **G11 结案为非缺口**（原文的「最严重一条」判定撤回）
- 一条命令：`node probes/g11-nondeterminism/run.cjs`（变异 `mutation.cjs` 7/7）
- 证据落盘：`probes/g11-nondeterminism/`（含三份历史产物）、`run-2026-10-22.txt`、`mutation-2026-10-22.txt`

---

## 1 登记时说的是什么

> G11 —— 同一份源码**两次构建产出不同的 C**：内建类字段有时被写成**文件作用域拼法**，
> 与手写内建体对不上 ⇒ **C 编译不过**。
> 判定：**遗留欠账**（且是本轮发现的**最严重**一条）：不是「哪个名字写错」，而是**生成结果不确定**。

当时的推断机制是：「有一趟把保留名表逐个按文件作用域命名并登记的过程跑了，**污染了块作用域的命名缓存**」。
这条推断**是错的**，而它错得体面：所有观察都是真的，只有「两次构建之间什么没变」这个前提是假的。

## 2 三条互相独立的判据

### 判据 ① 时间线：失败构建夹在「改名机制正被改写、尚未提交」的窗口里

| 时刻（`+0800`） | 事件 | 来源 |
|---|---|---|
| 04:00:10 | 编译器会话自己的探针产物 `temp/gapprobe/nc-bind2.c`：`struct Date { double time__; }` + `offsetof(Date, time__)`，而手写体是 `o->_time` | 文件 mtime |
| **04:00:19** | **我这次登记的失败构建**（`probes/array-scope/cc.txt`，坏 C 同目录） | 文件 mtime |
| 04:00:50 | `nc-bind3.c`：`Date` 修好，剩 **1** 处（`socket`） | 文件 mtime |
| 04:01:34 | `nc-bind4.c`：**0** 错，并产出 `nc-bind4.exe` | 文件 mtime |
| **04:24:34** | 提交 `721e12f`（阶段二百四十七：保留名表机器生成 + 文件作用域改 `__` 后缀） | `git log -1 --format=%cI` |
| 05:11:26 | 我在已提交树上复建 `Main.c`：`double _time;`、`offsetof(Date, _time)`，通过 | 文件 mtime |

⇒ 失败那次距修复提交 **24 分钟**；而**同一程序**在 **84 秒**内 20 → 1 → 0 条错。**单调收敛是人的编辑，不是随机。**

### 判据 ② 同一状态的另一份产物：hazard 集逐项相同

我的失败日志与 artifact-1（比我早 9 秒、**另一个程序**、由上游会话自己的探针产出）坏在**同一组**三个字段上：

```
我的构建 (04:00:19)      : Date._time, TextField.___restrict, ServerSocketConnectEvent.socket
artifact-1 (04:00:10)   : Date._time, TextField.___restrict, ServerSocketConnectEvent.socket
```

同一份日志里，`clang` 报 19 条真错 + 1 条 `fatal error: too many errors emitted` 哨兵 —— 登记时记的「20 个错」
把哨兵算进去了，而 `-ferror-limit` 默认就是 20：**「上限」当时被当成了「这个文件的属性」**（已就地更正）。

### 判据 ③ 冻结树上确定性成立

同一 HEAD + 同一 **92 份输入的输入哈希**，连续 **5 次**构建：

```
input: 92 .as files, sha256/16 d7fae1ddd878e83e (0 missing)
run 1..5: 3698965 B  sha256/16 f0ac0ff461e604bf   (各 6.7~6.8 s)
input hash after the runs: d7fae1ddd878e83e (unchanged)
distinct hashes: 1 of 5  -> ONE output for one input
```

⇒ 生成结果是 **(输入, 编译器源码树) 的确定函数**。所以「两次构建不同」**只能**意味着其中一个因子变了。

## 3 真正的机制（登记时的推断被推翻）

上游最终提交的设计正是**拒绝**那个中间态，提交信息写得很直白：

> `src/emit.ts`：… `cIdent` **刻意不动** —— 内置类方法体是手写 C 字符串、字段名逐字写死，
> 放宽块作用域会让 struct 与自身方法体脱节。

`src/symbols.ts` 里 `C_RESERVED_SCOPE` 上方还留了同型反例（就是 `socket`）。也就是说：

- **不是**「命名缓存被污染」；
- **是**「文件作用域改 `__` 后缀的那次改动，把结构体字段也带上了文件作用域路径」，
  而手写体字面量仍是块作用域拼法 ⇒ `struct Date { double time__; }` 与 `o->_time` 脱节。

残余风险如实记：**只要把结构体字段也路由到 `sanitizeFileCIdent`，这个坏法立刻回来**。现在它有
**双面守卫**——设计注释 + 拼写钉子 `unit: emit/CNameCollision`（16 条；阶段二四七变异实测：
`suffix→prefix` 时示例仍绿而**钉子红**）+ 文档 `docs/zh-cn/c-naming.md` §8（中英两侧）。
⇒ 缺口关闭，风险转为**有钉子的设计约束**。

## 4 处置变更（旧处置已废止）

| | 旧 | 新 |
|---|---|---|
| 看到 `_time` / `___restrict` / `socket` 这类指向没写过代码的 C 错 | 「**先原样重跑一次构建**」 | 先看编译器树：`git -C as3compiler status --porcelain`。有**已跟踪文件被修改**就是可复现条件 ⇒ 等提交或换干净树；一条命令给结论 `node probes/g11-nondeterminism/run.cjs` |
| 两个 demo runner | 构建**重试 3 次**（G11 注释） | **不重试**，改为每次打印编译器树状态（`ui-demo/air-run.cjs::compilerTree`）。理由：重试把真因藏起来，还会把真缺陷伪装成「第 2 次成功」 |

## 5 钉子与变异（本项目要求「有牙」）

`run.cjs` 五段测量：**A** 树状态（含 `src/` 内容哈希）· **B** 5 次构建同一哈希 + **输入哈希与 `src/` 内容哈希各测首尾** ·
**C** 拼写三处一致（struct / props 表 / 手写体字面量）· **D** 三份历史产物误差单调衰减 ·
**E** 与登记失败同 hazard 集。证据**追加**写 `run-<date>.txt`，**不覆盖**。

三种终止码对应三种事实（**这里有过一次设计修正**）：

| exit | 判定 | 条件 |
|---|---|---|
| `0` | **PASS** | 五段全绿 **且** `src/` 内容哈希在测量期间**未变**。树脏但稳定时 PASS 会点名内容哈希并注明：认证的是**该内容哈希**，不是提交 |
| `3` | **INCONCLUSIVE** | 五段全绿，但编译器源码**中途变了** —— 给绿等于给一棵没钉住的树背书，给红等于把别人的未提交改动算到本工作区头上。门把它报成**响亮的 `[SKIP]`** 并单独计数 |
| `1` | **FAIL** | 某个测量真的不对（多个哈希 / 拼写不一致 / 产物不衰减 / hazard 集不符） |

> 初版把「树脏（相对 `HEAD`）」直接判红。那是**错的判据**：本机另一个会话常年在改 `src/`，
> 于是这道门会变成「看运气的红」，没人会再信它。真正决定有效性的是**生成器版本在测量期间有没有动**
> —— 既更严格（钉的还是关键那个东西），又不受别人未提交改动影响。这是本轮第二次「先修仪器」。

`mutation.cjs` **8/8**（5 组变异，全部 `finally` 还原 + sha256 核对）：

| 变异 | 改什么 | 必须变红 |
|---|---|---|
| M1 | **健康**产物 artifact-3 只改结构体字段 `_time` → `time__` | clang 报 `no member named '_time'`（**用好的文件一个令牌造出 G11 的形状**） |
| M2 | artifact-3 的 props 项 → `offsetof(Date, nope)` | clang 点名 `nope`（与 M1 合起来证明两侧都读文件） |
| M3 | `Main.as` 一个字符串字面量 | 生成 C 的哈希**必须变**（否则「5 次同一哈希」可能是个常数，等式空洞） |
| M4 | `run.cjs` 自己的期望值（artifact-3：0 → 1 错） | 门以 `FAIL: artifact-3-consistent.c` 变红 |
| M5 | `ASC_G11_FORCE_SKIP=1`（假装生成器在测量期间动过） | 必须 **INCONCLUSIVE + exit 3**，且**不得**出现 `PASS:` —— 否则这个测试钩子就能把一次没测成的跑法洗成绿的 |

**变异暴露的两个「仪器缺陷」**（比缺陷本身值钱）：

1. **M2 首轮假红**：clang 的措辞有两种 —— `in 'struct Date'`（变量接收者）与 `in 'Date'`（类型）。
   断言只钉了前一种 ⇒ 把谓词放宽成 `in '(?:struct )?'`（`run.cjs` 的 hazard 提取同样修正）。**是仪器错，不是系统错。**
2. **D 段期望值原本写死 `20`**：那是 clang 的错误**上限**，不是文件的属性（`-ferror-limit=20`）。
   改成 `truncated: true` + `>= 16`，并记录 clang 自己的汇总行 —— 钉上限会让探针在 clang 升级时假红，且什么都没证明。

## 6 顺带证实：这台机器上，编译器树**真的**在被并发改写（而且这次看到了全程）

写这份文档期间，`run.cjs` 的 A 段亲眼看到编译器工作树：

- **21:56 UTC**：clean（只有未跟踪的 `?? icudtl.dat`）
- **22:03 UTC**：` M src/air-app.ts | M src/index.ts | M src/reach.ts | M test/unit/reach.ts`
- **22:24 UTC**：**它们被提交了** —— `5b47fc1`（阶段二四九：G13 闭包修复）→ `1ac26b4`（阶段二五零：`--as-class-path`），工作树回到 **clean**

这不是为文档编的理由，而是**当场抓到的全程**（脏 → 提交），也是 A 段为什么是测量的一部分、而不是脚注。
⇒ 因此有效性判据必须是「**测量期间源码有没有动**」而不是「树脏不脏」：在**稳定但脏**的树上，
「同源同 C」是**可以**测的；只有**测量期间源码真在动**，才算测不了（exit 3 / 门的 `[SKIP]`）。

**一个意外的交叉验证**：我在**脏树**上（22:16 UTC）测得的 `src/` 内容哈希是 `d7d7f962fa2eb80b`；
上游提交后，在 **clean 树**上（22:34 UTC）重测，同一个哈希 —— 因为提交**不改变内容**。
也就是说：我那次 PASS 认证的就是后来成为 `1ac26b4` 的那份**逐字节相同**的源码，
而它当时还没被提交。两次测量（脏 / 净）的生成 C 哈希也一致：`f0ac0ff461e604bf`、3698965 B、各 6.8~6.9 s。
同时，那个残留的 `icudtl.dat` 已被上游会话删除（`git status` 现为完全 clean）。
