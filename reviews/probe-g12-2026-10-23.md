# G12 结案：不是运行时缺陷，是见证程序自身写错

**日期**：2026-10-23
**编译器**：`as3compiler` HEAD `6121b30`（v0.4.212），工作树 CLEAN，**本轮零改动**
**结论**：G12 **不是编译器/运行时缺陷**。`compiler-gaps.md` 的 G12 已改为「不是缺口」，
见证程序 `probes/array-scope/Main.as` 已修正，`tools/repro-array-scope.cjs` 已加固
（不再丢弃 stderr）。

---

## 1 登记时的结论

`compiler-gaps.md` 原文：**先分配大字节缓冲（`ByteArray` / `BitmapData`），随后任何堆分配
（`push` 首个元素）会挂起（不是崩溃）**。判据是「进程还活着、帧号不前进、日志停在该语句上」。
产生解释写的是「`gc_in_heap()` 只做地址范围检查，134400 字节 `malloc` 落在 GC 段保留区间内
⇒ 标记切片按垃圾 `gc_header` 走 free-list ⇒ 死循环」，并注明**该解释未经源码验证**。

复现命令 `node tools/repro-array-scope.cjs` 在本轮开工时**仍然复现**：

```
churn 7 allocated a 134400-byte ByteArray
step 8 enter, frames=15 gcHeap?
churn 8 enter, frames=15
---- verdict ----
process alive when observed: true
done file: (none)
REPRODUCED (runtime): the log stops at "churn 8 enter, frames=15"
```

`reviews/repro-g12-2026-10-23b.txt` 是这次原始复现的输出。

## 2 定位过程（三步，每步都推翻一个假设）

### 2.1 头文件级 headless 复现：不复现

`temp/g12/a1.as`（`ba.length = 134400` → `aFresh.push(1)`）与 `a2.as`（5000 条字符串预热 /
`BitmapData.getPixels` / 大缓冲后连推 2000 个数组）**全部通过**。⇒ 不是「分配器被大块污染」
这种进程无关的确定性缺陷，必须回到窗口/帧循环环境里看。

### 2.2 给运行时插桩（临时，已全部还原）

在 `src/runtime.ts` 的 `gc_alloc` / `gc_find_block` / `gc_sweep_step` /
`gc_release_empty_segs` / `gc_mark_roots` / `gc_step` / `as_array_push` 里加了一个
`ASC_G12_TRACE` 门控的文件日志（大缓冲分配后自动 armed，只记录之后的窗口）。实测：

- 全程 **没有** free-list 死循环：`find-node` 最长连续 113 个节点就命中。
- 进程**没有挂住**：日志时间戳一直推进到被 kill 的那一刻，帧循环照常跑（14 秒内 346 帧，
  ≈24 fps），每帧都在分配。
- 真正停止的是 **`tick` 定时器回调**：日志最后一行是 `churn 8 enter`，之后 346 帧里
  只重复每帧一次的 UI 空闲分配（同一 40 项序列重复 560 次）。

⇒ 「进程活着 + 日志停」不等于「挂起」：**是回调死了，帧循环还活着**。

### 2.3 在 AS3 侧包 try/catch：一句话拿到真因

`probes/g12-as/Main.as`（现存档为 `probes/g12-ab/trycatch.as`）把 `aFresh.push(1)` 与
整个 tick 体各包一层 `try/catch` 写日志：

```
churn 8 about to push
PUSH THREW: 1009 Error #1009: Cannot access a property or method of a null object reference.
TICK THREW: 1009 Error #1009: Cannot access a property or method of a null object reference.
```

**`aFresh` 是 `null`。** 原因在见证程序本身：

```as
stage.showWindow(80, 60, "probe array-scope");   // 平台事实：不返回，把主线程交给消息循环

...
var aBuf:Array = [];      // ← 这三个脚本作用域变量声明在 showWindow 之后
var aFresh:Array = [];    //    初始化语句永不执行 ⇒ 引用类型停在零值 NULL
var bigBuf:ByteArray = null;
```

同一份文件顶上自己写着「`showWindow()` 不返回，所以每个 setup 步骤和每个必须触发的
`setTimeout` 都要在它**之前**注册」—— 定时器照做了，容器变量没照做。步骤 1~6 用的是
`aInts` / `aObjs`（声明在 `showWindow` 之前）所以全绿；`bigBuf` 只在 churn 里被**赋值**，
给 NULL 槽赋值当然成功；到 churn 8 第一次**读** `aFresh` 才炸。

## 3 三个变体的 A/B 实测（`probes/g12-ab/`）

每个变体都只改一处，全部重新构建整套 kit（与真应用同构）。

| 变体 | 改动 | 实测 |
|---|---|---|
| `nobuf.as` | **删掉** `bigBuf.length = 134400`（全程没有大分配） | 日志**照样**停在 `churn 8 enter`，stderr `Uncaught exception: Error #1009`；插桩计数里 `GCT_BYTES >= 128 KB` 的分配次数为 **0** |
| `fixed.as` | 三个容器移到 `showWindow` **之前**，134400 大缓冲保持不变 | `step 8/9/10` 全过 → `DONE`，done 文件 `PASS` |
| `trycatch.as` | 保持原声明顺序，只把 `push` 包进 try/catch | 打印 `PUSH THREW: 1009 ...` / `TICK THREW: 1009 ...` |

`nobuf.as` 是关键：**去掉所谓成因，症状一字不差** ⇒ 「大缓冲导致下一次堆分配挂起」这个
因果链不存在。`fixed.as` 再证：大缓冲原封不动，程序跑完。

修正后的见证程序现已全绿（`reviews/repro-g12-2026-10-23c.txt`）：

```

step 10 enter, frames=19 gcHeap?
DONE
---- verdict ----
done file: PASS
NOT REPRODUCED: the build was fine and the log reached DONE.
```

## 4 为什么这次误判值得记下来（两条，都是**诊断工具**问题，不是运行时问题）

1. **`stderr` 被丢弃。** 运行时对未捕获错误的行为是 AIR 式的：报一行
   `Uncaught exception: <msg>` 到 `stderr`，然后**不终止进程**（`src/runtime.ts`
   第 6169~6238 行一带）。`tools/repro-array-scope.cjs` 当时以 `stdio: 'ignore'` 启动，
   连同见证程序自己「stdout 被丢弃」的设计，两路输出全没了 —— 一个 `TypeError`
   于是长成了「静默挂起」。**已修**：工具现在收 `stderr`，并在日志里显式打印；
   判定新增 `REPRODUCED (uncaught)` 分支。用未修正的 `nobuf.as` 反证过该分支
   （`reviews/repro-g12-uncaught-branch.txt`）。
2. **「帧号不前进」被当成「帧循环停了」。** 帧号是 tick 自己打的，tick 一死它当然不前进；
   真实信号应该是「窗口是否还在响应」或运行时自己的帧计数。这一条不改工具，
   但写进 `probes/array-scope/Main.as` 的头注释：日志停 ≠ 进程挂。

## 5 顺带量到的事实（供登记，不是缺口）

- **`stage.showWindow()` 不返回**是我们窗口后端的设计事实（把主线程交给帧/消息循环），
  `examples/*.as` 与探针注释里都按这个前提写。它的直接后果是**顶层语句在
  `showWindow` 之后的都永不执行**，包括 `var x = <初值>` 的初值。
  AIR 桌面端 `showWindow`/`visible = true` 不阻塞，所以同一份源码在 AIR 里这些变量会被
  正常初始化。⇒ 这是**已知的平台差异**，本轮不立项（要改成非阻塞得动整个事件循环架构）。
  但它是 G12 的真实来源，已在探针头注释与本文记录，避免下次再被诊断成堆缺陷。
- `Uncaught exception: ...` 目前写到 `stderr`，文案 `adl` 侧尚未逐字对齐
  （`src/runtime.ts` 里已自我标注为未结项），与本条无关。
