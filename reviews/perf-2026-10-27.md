# 性能排查（2026-10-27）：三处写法级热点，不是引擎问题

起点是用户的一句「我感觉性能有重大问题」。这次没有靠读代码下结论：先写计时探针
`probes/perf`，再用「临时摘除一个机制 → 重编 → 重测 → 逐字节还原」把每一毫秒
归到具体环节。所有变异脚本在 `temp/{dissect,dissect2,bisect}.cjs`，还原都带 sha256 校验。

## 测量对象

300 个带 key 的 `button`（一个 column），AOT native，每相位 10 次取平均。
相位：`idle`（无 pending）、`describe`（`invalidate` 但作者什么都没改）、
`layout`（300 个文案全变）、`one`（**只有 1 个**文案变，即真实 keystroke 的形状）、
`solve`（只调引擎）、`resolve`（全树 re-resolve，主题切换路径）、`paint`（单节点重绘）。

## 结果（毫秒）

| 相位 | 修前 | 修后 | 倍数 |
|---|---|---|---|
| idle | 0 | 0 | —（稳态零工作本来就是真的） |
| describe（无变化） | **39.3** | **1.0** | 39× |
| one（单点文本变化，整帧） | **13.3** | **1.7~2.0** | ~7× |
| layout（300 个文本全变） | 47.2 | 9.2 | 5× |
| resolve（全树，主题切换） | 40.5 | 1.6 | 25× |
| solve（纯引擎） | 0.3 | 0.3 | 不是瓶颈 |
| paint（单节点） | 0 | 0 | 不是瓶颈 |

## 三根因

### 1. 重复 key 检查是 O(n²) —— 占 describe 的 98%

`Reconciler.reconcileChildren` 的重复 key 检查写成嵌套循环，每个父节点每次 describe
做 n(n-1)/2 次 `internKey`，而 `internKey` 每次都拼 `"s:" + key` 字符串。
300 个兄弟 ⇒ 44,850 次字符串拼接，**每一帧**。

摘除它：39.2 → 0.7ms。摘除「顺序没变也重排引擎/显示列表」：39.1ms（**无影响**）。

修法：intern 后的 id 已是唯一正整数，改用 seen-set 一遍扫完，抛错文案不变。
`kit/asaot/ui/Reconciler.as`。

### 2. 文本测量没有缓存 —— 占 layout 的 85%

`no measurePass` 变异：layout 9.4 → 1.7ms。`no paint` 变异：**0 影响**。
也就是说钱花在海量 `TextField` 整形上，不在画笔上。

`PaintKit.measureField` 每次都 `new TextFormat()` + `field.text = content`（重建 run
table）+ `setTextFormat`（再建一次）+ 读 `textWidth`（强制整形），而 measurePass 是
**全树**的。`ElementState.measureValid` 只写不读——缓存位存在，缓存不存在。

修法：两个 key（`UiNode.measureKey` / `formatKey`）。
- `measureKey` = 文本 + wrap 宽 + 字体度量字段 ⇒ 命中就跳过 `field.text=` 与测量读。
- `formatKey` = 上面 + **颜色** ⇒ 命中就跳过 `setTextFormat`。

**颜色必须只在第二个 key 里**：第一版只有一个不含颜色的 key，`probes/widgets/motion`
立刻抓到——文字颜色 tween 永远到不了白色，因为「应用格式」一直是测量的副作用。
拆开之后，变色只重设格式、不重新整形。

### 3. 一个被否决的「优化」

把 layout 后的 `paintAll` 换成 `paintDirty`：`probes/widgets/stick` 全红
（sticky 带不跟随），而且 `no paint` 变异显示它**省不下任何时间**。
已回退，`UiApp.reflow` 里留了注释：不要再优化这一行，除非两个探针都重跑。
`UiNode.arrangeSelf` 的「尺寸变 ⇒ 标 M_PAINT」保留（无害且语义正确）。

顺手：`UiNode.resolveStyle` 里 `Style.diffFlags` 原本算两遍，改为复用局部 `f`。

## 牙齿

`probes/perf` 只有一条断言：无变化 describe 超过 **15ms** 即 FAIL
（好的 1.0ms、坏的 39.3ms，15 倍余量不会抖，二次方回来必被抓）。
实测把嵌套循环放回去 ⇒ `40.7ms` ⇒ 红。已挂进 `tools/gates.cjs`（第 58 道）。

## 还没做、但知道的

- **任何 notify 都是全树 re-describe + 全树 measurePass**。单点变更现在 1.7ms/300 节点，
  节点数上万仍会疼；真正的解法是子树级 describe/测量，那是架构改动，不在本轮。
- `Style.clear()` 每次 `new TextStyle()`；`Theme.resolve` 每节点 4 次全字段拷贝。
  在 300 节点规模下是零头，没动。
- 窗口后端每帧 present 所有可见窗口（`UiApp` 头注释），库侧管不到。
